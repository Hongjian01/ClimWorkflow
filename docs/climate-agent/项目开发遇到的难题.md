# 项目开发遇到的难题

记录 2026-09-18 本机真实 CDS + TUI（`deepseek-v4-pro` / `full_auto`）暴露的两类问题。二者都会让 `climate_acquire_data` 看起来「一直在跑」，但根因不同，修复日也不同。

观测 run：`d74b274c-41a8-4c29-bca2-9b8bf19d6f03`。pytest `climate_integration` 已 `2 passed`（约 29 分钟），说明 **CDS 账号、许可、裁切、NetCDF 发布在非 TUI 路径上是通的**。

---

## 难题 A：填表失败（模型方言 ≠ 七键合同）

### 现象

`init` / `plan` 一次成功，意图已对齐（北京、2 米气温、`mode=cds`、禁止 sample）。随后 `climate_acquire_data` 连续 `CLIMATE_INVALID_INPUT`：

| 次数 | `field` | 含义 |
|---|---|---|
| 1 | `variables` | 用了 `t2m` 或未登记名；目录要 CDS 长名 `2m_temperature` |
| 2 | `date_start` | 不是 `YYYY-MM-DD` 合法闭区间 |
| 3 | `product_type` | CDS 门户字段；本系统禁止，内部写死 `reanalysis` |
| 4 | `time` | 门户小时列表；本系统禁止，内部展开 24 小时 |

这是 **槽位映射** 失败，不是「没听懂任务」。

### 根因

- 没有独立 NLU。路径是：用户中文 → LLM tool call → 外层 `cds_request: dict[str, Any]` 先过 → 内层 `CdsRequestInput(extra=forbid)` 才打回。
- 发给模型的 JSON Schema 几乎看不到七键和变量枚举，模型按 CDS 官网 / NetCDF 短名填表。
- 打回是 **内层 Pydantic** 变成稳定错误码 envelope，QueryEngine 让模型改参再调（ReAct），不是框架自动填表。

### 不属本题

- 不是 QueryEngine 坏了，也不是目录闸门失效。
- 不能靠默认打开 `climate_query_knowledge` 当主修复：`t2m` 仍不能当 CDS 变量名。
- 不能静默删除 `product_type` / `time` 后当成功。

### 修复口径

**Day 22 / DEC-G5-002**：把内层合同提前暴露到 `to_api_schema()`（方案 B），Skill 补合法 JSON 与禁止字段。运行时仍 `parse_cds_request`，保持 `CLIMATE_INVALID_INPUT`。详见 [DAY_22_G5_CDS_TOOL_SCHEMA.md](daily/DAY_22_G5_CDS_TOOL_SCHEMA.md)。

Schema **解决不了** 填对之后的 retrieve 挂起（难题 B）。

## 难题 B：网页已成功，TUI 仍 Running（retrieve 收尾）

### 现象

| 位置 | 事实 |
|---|---|
| CDS 网页 | 例如 21:37:05–21:37:31 Successful，25.26 KB（约 25 秒） |
| 磁盘 | `.part` 大小与网页一致，时间紧挨着，文件头为合法 NetCDF-4 |
| Context / TUI | acquire 仍 `running`，没有正式 `.nc`，工具不返回 |

慢的不是传 30 KB，而是：（1）CDS 排队裁切；（2）更关键——**文件已经写完，`retrieve()` 还不返回**。校验和 `os.replace` 都排在 `retrieve()` 之后，所以工作流不能收尾。

`climworkflow resume` 只读 Context，不会把 `.part` 收成成功；下一次 mutation 还会按中断恢复 **删除** `.part`。

### 根因（两层叠在一起）

**第一层：第三方客户端把「写完磁盘」和「函数返回」绑死。**

PAT 无冒号时走 `LegacyClient` → `submit_and_wait_on_results` → `multiurl` 流式 `iter_content`。循环要等连接结束；服务端 Keep-Alive 不关连接时，`.part` 已齐、Python 仍阻塞。`Client(timeout=60)` 不是整次 retrieve 的墙钟超时。CDS-003 只在 **抛出** timeout/429 时重试；永不返回则不失败、不重试、不发布。

**第二层：这条阻塞调用跑在 TUI 的 asyncio 事件循环线程上。**

`QueryEngine` 是 `await tool.execute(...)`（合法异步合同）。`ClimateAcquireDataTool.async execute` 内部却同步调用 `retrieve()`，没有 `asyncio.to_thread`。Textual 靠同一条循环刷新：

- 界面只能停在 Running，即使 CDS 网页早已 Successful；
- tqdm / 日志往被 TUI 占用的终端写，Windows 上可能死锁。

pytest 没有 Textual，同一套 `cdsapi` 可以在约 29 分钟后返回。所以这不是「CDS 下不下来」，而是 **TUI 路径上的收尾与事件循环**。

归属见下文第三节口径：OpenHarness 缺口 + ClimWorkflow 适配错误，不是 QueryEngine 算错工具结果。

### 修复口径

**Day 21 / DEC-G4-002**：retrieve 墙钟超时 + 下载卸载出事件循环 + `.part` 大小稳定且 magic 合法即校验发布。详见 [DAY_21_G4_CDS_RETRIEVE_TIMEOUT.md](daily/DAY_21_G4_CDS_RETRIEVE_TIMEOUT.md)。

## 责任边界（对应「是不是 OpenHarness 的 bug」）

- **不是** QueryEngine 把成功判成失败：工具根本没返回。
- **OpenHarness 缺口**：`await execute` 不会自动把阻塞 IO 丢到线程；TUI 与工具共用事件循环。
- **ClimWorkflow 问题**：气候工具在 `async execute` 里做无界同步 `retrieve()`，且以客户端返回而不是「`.part` 已合法」为完成条件。
- **第三方**：`cdsapi` / `multiurl` 在连接不关闭时 `iter_content` 不结束。

完整论证见 Day 21 日计划「责任边界」节。
